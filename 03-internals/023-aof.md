# Lesson 023 — Redis AOF Persistence

> **Section 03 — Keys, Memory and Internals** | Intermediate → Advanced  
> **Goal:** Understand the Append Only File, fsync policies, multipart AOF, rewriting, crash recovery, and production trade-offs.

**Previous:** [Lesson 022 — RDB Persistence](022-rdb.md)  
**Next:** [Lesson 024 — Redis Recovery and Disaster Planning](024-recovery.md)

## 1. Why AOF exists

Redis works primarily in memory. An RDB snapshot records the dataset at a point in time, so writes made after the last successful snapshot can be lost during a crash.

**AOF (Append Only File)** records operations that modify the dataset so Redis can reconstruct its state after a restart.

Think of:
- **RDB:** a photograph of a whiteboard.
- **AOF:** a journal of changes to the whiteboard.

\`\`\`mermaid
flowchart LR
    A["Client writes"] --> B["Redis memory"]
    A --> C["AOF persistence path"]
    C --> D[("AOF files on disk")]
    D --> E["Replay/reconstruct on restart"]
\`\`\`

**Important:** AOF improves durability but does **not** guarantee zero data loss under every failure. The fsync policy, storage device, operating system, and replication setup all matter.

## 2. What gets written to AOF?

Redis records commands needed to reproduce changes to the dataset. Read-only commands such as \`GET\` do not need to be persisted.

Example:

\`\`\`redis
SET demo:counter 10
INCR demo:counter
HSET demo:user name Asha
DEL demo:counter
\`\`\`

The AOF persistence mechanism represents write effects so Redis can restore the resulting state.

Do not assume the on-disk representation always contains your exact original client command text. Redis may normalize or rewrite commands, and a rewritten AOF can describe the final state rather than preserving the entire original command history.

**AOF is a recovery mechanism, not a permanent application audit log.**

## 3. Enable and inspect AOF

Example configuration:

\`\`\`conf
appendonly yes
appendfsync everysec
\`\`\`

Inspect a running server:

\`\`\`redis
CONFIG GET appendonly
CONFIG GET appendfsync
INFO persistence
\`\`\`

In a disposable environment you can enable AOF with configuration, but changing persistence settings on production Redis needs planning because it can trigger I/O and rewrite work.

**Version note:** File layout, default settings, and some commands vary between Redis versions. Check your running server and its official documentation.

## 4. Understand buffering and fsync

Writing data involves more than one stage:

1. Redis processes the write.
2. The AOF data is written through the operating system's file interface.
3. The operating system may hold data in its page cache.
4. \`fsync\` requests that buffered data be synchronized to storage.

\`\`\`mermaid
flowchart TD
    A["Write command"] --> B["Redis dataset updated"]
    B --> C["AOF write to OS"]
    C --> D["OS page cache"]
    D --> E["fsync / storage synchronization"]
    E --> F[("Persistent storage")]
\`\`\`

**Key distinction:** “Written to the OS” is not the same as “guaranteed safe on physical storage.” Hardware and virtualization can also affect durability guarantees.

## 5. The three fsync policies

The \`appendfsync\` setting determines the fsync strategy.

| Policy | Meaning | Typical trade-off |
| --- | --- | --- |
| \`always\` | Request fsync for every write operation/batch | Stronger durability, higher latency/I/O |
| \`everysec\` | Request fsync approximately once per second | Common balance of performance and durability |
| \`no\` | Let the operating system decide when to flush | Less fsync overhead, potentially larger loss window |

### always

\`\`\`conf
appendfsync always
\`\`\`

Redis attempts to synchronize each write or batch. It can reduce the loss window, but performance depends heavily on storage.

**Do not interpret “always” as absolute zero-loss protection** against every hardware, filesystem, or deployment failure.

### everysec

\`\`\`conf
appendfsync everysec
\`\`\`

Redis normally fsyncs about once per second. A sudden failure can lose approximately the most recent second of writes under ordinary assumptions, but unusual stalls or storage failures can extend the practical window.

### no

\`\`\`conf
appendfsync no
\`\`\`

Redis leaves flushing to the operating system. Durability becomes less predictable.

### How to choose

- Rebuildable cache: RDB or no persistence may be sufficient.
- General-purpose Redis with useful state: \`everysec\` is a common starting point.
- Very strict durability: investigate \`always\`, but also evaluate whether a transactional database is the right source of truth.

## 6. AOF restart and replay

On restart, Redis can load persisted state from AOF files.

\`\`\`mermaid
sequenceDiagram
    participant App as Application
    participant R as Redis
    participant Disk as AOF storage
    App->>R: SET order:101 created
    R->>Disk: Persist write effect
    App->>R: HSET order:101 status paid
    R->>Disk: Persist write effect
    Note over R: Redis stops unexpectedly
    Disk-->>R: Load AOF data
    Note over R: Reconstruct saved state
\`\`\`

If both AOF and RDB persistence are enabled, Redis generally uses AOF to recover because it can be more recent than the last RDB snapshot.

**Important:** AOF recovery is not a cross-system transaction. A PostgreSQL write and a Redis AOF write are not automatically committed together.

## 7. Why AOF rewriting is necessary

Imagine a counter:

\`\`\`redis
SET demo:views 0
INCR demo:views
INCR demo:views
INCR demo:views
\`\`\`

After thousands of updates, the current value may be simple, but the accumulated AOF history could be large.

**AOF rewrite** creates a more compact representation sufficient to reconstruct the current dataset.

\`\`\`mermaid
flowchart LR
    A["Many historical writes"] --> B["AOF rewrite"]
    B --> C["Compact current-state representation"]
    C --> D["Smaller recovery workload"]
\`\`\`

Rewriting is **not** the same as deleting application history from a proper audit database. AOF was never intended to be that audit history.

## 8. BGREWRITEAOF

Trigger a background rewrite:

\`\`\`redis
BGREWRITEAOF
\`\`\`

On supported systems, Redis performs the rewrite in a background child process while the parent continues handling commands.

Monitor:

\`\`\`redis
INFO persistence
\`\`\`

Useful fields may include:
- \`aof_enabled\`
- \`aof_rewrite_in_progress\`
- \`aof_last_bgrewrite_status\`
- \`aof_current_size\`
- \`aof_base_size\`
- \`aof_last_cow_size\` (where available)

**Production warning:** Background rewriting can consume CPU, disk I/O, and copy-on-write memory. Do not trigger it casually during peak traffic.

## 9. Modern multipart AOF (Redis 7+)

Redis 7 introduced a **multipart AOF** design. Instead of assuming one ever-growing \`appendonly.aof\` file, modern Redis can manage:

- A **base** file representing a compact snapshot/state.
- One or more **incremental** files containing newer changes.
- A **manifest** describing the active file set.

\`\`\`mermaid
flowchart TD
    M["AOF manifest"] --> B["Base AOF/RDB-format file"]
    M --> I1["Incremental AOF file"]
    M --> I2["Later incremental AOF file"]
    B --> R["Recovery"]
    I1 --> R
    I2 --> R
\`\`\`

The base file may use RDB format when configured to do so. Redis uses the manifest to coordinate which files belong to the active dataset.

**Critical:** Do not manually copy only one AOF fragment and assume you have a complete backup. Capture a consistent set using a supported backup process.

### Inspect the directory

Relevant settings may include:

\`\`\`redis
CONFIG GET appendfilename
CONFIG GET appenddirname
CONFIG GET aof-use-rdb-preamble
CONFIG GET dir
\`\`\`

These options and file layout depend on Redis version.

## 10. Automatic AOF rewrite thresholds

Example:

\`\`\`conf
auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 64mb
\`\`\`

The rewrite mechanism considers how much the AOF has grown relative to its baseline and whether the minimum size is reached.

- \`auto-aof-rewrite-percentage 100\`: roughly trigger after 100% growth relative to the reference size, subject to other conditions.
- \`auto-aof-rewrite-min-size 64mb\`: avoid rewrites for very small AOF files.

These are illustrative configuration values. Verify your installed defaults and monitor actual rewrite behavior.

## 11. AOF rewrite, fork, and copy-on-write

Like \`BGSAVE\`, AOF rewriting can involve a child process and copy-on-write memory.

\`\`\`mermaid
flowchart TD
    A["Redis parent"] -->|"fork"| B["AOF rewrite child"]
    A --> C["Continue accepting writes"]
    B --> D["Write new base state"]
    C --> E["New incremental AOF data"]
    D --> F["Finalize updated AOF manifest/files"]
    E --> F
\`\`\`

During a heavy write workload, memory and disk pressure can increase.

### Production implications

- Reserve RAM headroom.
- Monitor disk free space.
- Monitor fork latency and copy-on-write.
- Avoid running persistence-intensive maintenance at peak load.
- Understand interactions with RDB background saving.

## 12. AOF corruption and partial writes

A process crash or storage failure can leave an incomplete tail or other AOF damage.

Redis has tools to inspect and repair certain AOF problems, including:

\`\`\`bash
redis-check-aof --help
\`\`\`

**Do not run a destructive repair against the only production copy.**

Safer approach:
1. Stop and isolate the affected instance when appropriate.
2. Preserve a copy of every relevant persistence file and manifest.
3. Determine Redis version and multipart AOF layout.
4. Validate using the corresponding Redis tools.
5. Repair only a disposable copy after understanding what data may be removed.
6. Test recovery before using the repaired dataset.

Settings such as \`aof-load-truncated\` can affect behavior for a truncated AOF tail. Truncation and corruption are not equivalent, and automatic loading is not a substitute for investigating the failure.

## 13. RDB vs AOF: detailed comparison

| Question | RDB | AOF |
| --- | --- | --- |
| What is persisted? | Dataset snapshot | Write effects / compact rewritten state |
| Typical durability | Since last successful snapshot | Depends on fsync policy |
| Disk space | Often compact | Can be larger; rewrite controls growth |
| Background maintenance | BGSAVE | BGREWRITEAOF |
| Restart | Load snapshot | Reconstruct from AOF file set |
| Backup convenience | Simple snapshot artifact | Consistent multipart file set needs care |
| Resource costs | Fork, disk writes, COW | Write I/O, fsync, rewrite, COW |
| Main strength | Compact point-in-time backup | Potentially smaller loss window |

**Neither option alone guarantees high availability.** Replication and failover solve different problems and can still lose acknowledged writes under some failures.

## 14. Using RDB and AOF together

A deployment may enable both:

\`\`\`conf
save 300 10
appendonly yes
appendfsync everysec
\`\`\`

Why?
- RDB can provide convenient point-in-time snapshots.
- AOF can offer more recent recoverable state.
- Separate backups improve disaster recovery.

Trade-offs:
- More disk I/O.
- Background save/rewrite resource usage.
- More operational complexity.

Choose based on measured load and recovery requirements, not a universal “always enable everything” rule.

## 15. Docker practical: enable AOF

Example \`compose.yaml\` for **local learning only**:

\`\`\`yaml
services:
  redis:
    image: redis:7
    command:
      - redis-server
      - --appendonly
      - "yes"
      - --appendfsync
      - everysec
      - --dir
      - /data
    ports:
      - "127.0.0.1:6379:6379"
    volumes:
      - redis_aof_data:/data

volumes:
  redis_aof_data:
\`\`\`

Start:

\`\`\`bash
docker compose up -d
docker compose exec redis redis-cli SET demo:aof "hello"
docker compose exec redis redis-cli INFO persistence
\`\`\`

Restart:

\`\`\`bash
docker compose restart redis
docker compose exec redis redis-cli GET demo:aof
\`\`\`

Expected: \`hello\`.

**Caution:** A clean restart is not a test of every sudden-crash failure mode. AOF behavior during an abrupt power loss depends on fsync policy and storage.

**Never run \`docker compose down -v\` on a volume you need to preserve.**

## 16. Real-world example: order processing

Suppose your Node.js service writes an order to PostgreSQL and sends an event to Redis Streams.

\`\`\`mermaid
flowchart TD
    API["Order API"] --> DB[("PostgreSQL order + outbox")]
    DB --> P["Outbox publisher"]
    P --> S[("Redis Stream")]
    S --> AOF["AOF persistence"]
    S --> W["Consumer group workers"]
\`\`\`

AOF reduces certain Redis data-loss risks, but the PostgreSQL transactional outbox is still important.

Why?
- PostgreSQL and Redis do not share one transaction.
- AOF fsync is not necessarily immediate.
- A consumer can crash after completing a side effect but before acknowledging.
- Retries can produce duplicate events.

**Design workers to be idempotent.**

## 17. Node.js: inspect AOF state safely

Install:

\`\`\`bash
npm install redis
\`\`\`

ESM example:

\`\`\`js
import { createClient } from "redis";

const redis = createClient({
  url: process.env.REDIS_URL ?? "redis://127.0.0.1:6379",
});

redis.on("error", (err) => console.error("Redis error:", err.message));

try {
  await redis.connect();

  const info = await redis.info("persistence");
  console.log(info);

  const appendonly = await redis.sendCommand([
    "CONFIG", "GET", "appendonly",
  ]);

  console.log("AOF config:", appendonly);
} catch (err) {
  console.error("Inspection failed:", err.message);
  process.exitCode = 1;
} finally {
  if (redis.isOpen) await redis.quit();
}
\`\`\`

**Production note:** Redis ACLs or managed providers may restrict \`CONFIG GET\`. Use approved monitoring endpoints when direct configuration inspection is unavailable.

## 19. Common mistakes

1. Assuming AOF means zero data loss.
2. Confusing an OS write with an fsynced write.
3. Choosing \`appendfsync no\` without accepting its risks.
4. Assuming AOF always consists of one file.
5. Manually copying a single incremental AOF file as a complete backup.
6. Triggering rewrites during peak traffic without capacity planning.
7. Ignoring disk space and copy-on-write memory.
8. Using AOF as a permanent audit log.
9. Treating Redis and PostgreSQL writes as one transaction.
10. Repairing a corrupted AOF without first preserving the original.
11. Forgetting persistent Docker storage.
12. Never testing restart and disaster recovery.

## 21. Interview questions

**Q1. What is AOF?** Redis persistence based on recording write effects for later reconstruction.

**Q2. What is appendfsync everysec?** Request an fsync approximately once per second.

**Q3. Does everysec guarantee at most one second of data loss?** Not under every failure; unusual stalls and storage behavior can increase the practical loss window.

**Q4. What is BGREWRITEAOF?** A background process that creates a more compact AOF representation of current data.

**Q5. Why rewrite AOF?** To prevent unlimited growth from historical updates.

**Q6. What is multipart AOF?** Redis 7+ organization using base/incremental files and a manifest.

**Q7. Why can AOF rewrite increase memory usage?** Fork and copy-on-write during concurrent writes.

**Q8. RDB vs AOF?** Snapshot vs write-log-oriented persistence.

**Q9. Can AOF replace PostgreSQL transactions?** No.

**Q10. Is an AOF file a complete offsite backup?** Not by itself; consistent file capture and restore testing are needed.
